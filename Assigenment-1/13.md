# Objective 1: Requirements Formulation

## 1. Domain and Problem Statement
<!-- Owner: A -->

### 1.1 Domain

The domain chosen for this assignment is banking, specifically credit card fraud detection. Card payments happen in very large numbers every day, and each payment has to be approved or declined within a few seconds. When a fraudulent payment is approved, the bank usually has to bear the loss, and the customer loses confidence in the bank. For these reasons we felt this is a practical area in which a machine learning based application can be useful.

### 1.2 Problem Statement

Banks lose a significant amount of money every year because of fraudulent credit card transactions. Manual checking by the fraud team is too slow to stop a fraudulent payment while it is being processed. Fraud cases are also very few compared to genuine transactions (less than 1%), so fixed rules either fail to catch them or end up blocking many genuine customers.

In this assignment we propose a fraud detection application that checks each card transaction as it arrives and gives a probability that the transaction is fraudulent. Transactions with a high score are flagged as suspicious, and the bank's fraud analysts review the flagged cases instead of checking every transaction. Our target is to detect at least 90% of fraudulent transactions while wrongly flagging less than 2% of genuine ones, and to return the result quickly enough to be used during the payment.

### 1.3 Why Machine Learning is Needed

Most banks already use rule-based checks, for example blocking a payment above a fixed amount or from an unusual country. These rules are written manually and fraudsters gradually learn how to avoid them. A rule also looks at only one or two fields at a time, and making the rules stricter causes more genuine payments to be declined.

A machine learning model can learn fraud patterns from past transactions that are already labelled as fraud or genuine. It can consider many features together, and it can be retrained when new fraud patterns appear. Since the model gives a probability rather than a simple yes or no, the bank can also choose a threshold that gives an acceptable balance between missed fraud and false alarms.

### 1.4 Stakeholders

| Stakeholder | Interest in the system |
|---|---|
| Bank risk manager | Reduce fraud losses without increasing complaints from customers |
| Fraud analyst | Get a reliable score so that only suspicious transactions need manual review |
| Card holder (customer) | Genuine payments should not be declined |
| ML and development team | Build and maintain a model and service that are accurate and fast |

### 1.5 Scope

The following are within the scope of this assignment:

- Checking a single transaction and returning a fraud label with its probability
- Providing this check through a prediction service (API)
- Training the model and storing it in a model registry
- Logging every prediction made by the service

The following are outside the scope: connecting to a real payment network, sending alerts to customers, handling chargebacks, and using real customer card data. We use a publicly available anonymised dataset instead.

### 1.6 Formulation as a Machine Learning Problem

We treat this as a binary classification problem, where each transaction is labelled either fraud (1) or genuine (0). The input to the model is the set of transaction features, and the output is the probability of fraud along with a final label based on a chosen threshold.

For this work we use the "Credit Card Fraud Detection" dataset available on Kaggle. It contains card transactions made by European card holders, with around 284,000 transactions of which only about 0.17% are fraud. <!-- unverified until the dataset is downloaded and checked (D1) --> Apart from Time and Amount, the features (V1 to V28) are already anonymised by the dataset provider. Because the two classes are so unbalanced, accuracy alone is not a useful measure (a model that marks everything as genuine would still be 99.8% accurate). We therefore evaluate the model using recall, precision, F1 score, the area under the precision-recall curve and the confusion matrix.

For the system design, we have selected two architectural patterns: Pipe-and-Filter for the model training pipeline, and Microservices for serving the model as a separate prediction service along with a model registry. These are explained in Section 6.
