# Objective 1: Requirements Formulation

## 1. Domain and Problem Statement  *(Owner: A)*

### 1.1 Domain

**Banking / digital payments – credit card fraud detection.**
Card payments are high-volume and time-critical, and every missed fraud is a direct financial loss and a loss of customer trust. This makes it a strong, realistic ML use case.

### 1.2 Problem statement

Banks lose money to fraudulent credit card transactions, and manual review is too slow to stop fraud while a payment is being made. Fraud is also rare (well under 1% of transactions), so simple fixed rules either miss it or block many genuine customers. We propose an ML-based fraud detection service that scores every transaction in real time and returns a fraud probability. The bank's fraud analysts can then allow, block or send the transaction for review. The goal is to catch at least 90% of fraud while wrongly flagging fewer than 2% of genuine transactions, with a response fast enough to be used during payment.

### 1.3 Why machine learning (and not fixed rules)

| Limitation of rule-based checks | How ML helps |
|---|---|
| Rules are written by hand and fraudsters learn to avoid them | Model learns patterns from past labelled transactions and can be retrained as fraud changes |
| Rules look at a few fields at a time | Model combines many features at once |
| Strict rules block genuine customers | Probability score lets the bank choose a threshold that balances misses and false alarms |

### 1.4 Stakeholders

| Stakeholder | Interest |
|---|---|
| Bank risk manager | Lower fraud losses and fewer false alarms |
| Fraud analyst | Clear risk score to decide allow / block / review |
| Customer | Genuine payments go through without being blocked |
| ML / engineering team | Model and services that are accurate, fast and maintainable |

### 1.5 Scope

- **In scope:** score a single transaction in real time; return label and probability; expose results through the FastAPI `/docs` page; train and register the model; log predictions.
- **Out of scope:** integration with real payment networks, customer notifications, chargeback handling, and real card data (we use an anonymised public dataset).

### 1.6 ML problem framing

| Item | Choice |
|---|---|
| ML task | Binary classification (fraud = 1, genuine = 0) |
| Input | Transaction features (anonymised components V1–V28, Time, Amount) |
| Output | Fraud probability and a label at a chosen threshold |
| Dataset | Kaggle "Credit Card Fraud Detection" (European card transactions, about 284,000 rows, about 0.17% fraud) |
| Main challenge | Highly imbalanced classes, so accuracy alone is misleading; we track recall, precision and PR-AUC |

**Architectural patterns selected:** Pipe-and-Filter (ML training pipeline) and Microservices (prediction API and model registry as separate services).
